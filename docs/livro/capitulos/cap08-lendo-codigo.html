CAPÍTULO 08

Lendo o código de uma lib

A estratégia é achar um programa que já faz o que você quer e seguir as chamadas até a biblioteca. O binário buildah é só um cliente da biblioteca buildah, então o código dele é o melhor manual.

  1. Clone e leia o go.mod. 
    git clone --depth 1 https://github.com/containers/buildah.git
head -1 buildah/go.mod        # module go.podman.io/buildah
  2. Ache o comando. cmd/buildah/build.go, função buildCmd. As três linhas que importam: 
    options, containerfiles, removeAll, err := buildahcli.GenBuildOptions(c, inputArgs, iopts) // flags → struct
store, err := getStore(c)                                                                 // storage local
id, ref, err := imagebuildah.BuildDockerfiles(getContext(), store, options, containerfiles...)
  3. Leia a assinatura com GOOS=linux GOFLAGS=-mod=vendor go doc ./imagebuildah BuildDockerfiles, rodado dentro do clone.
  4. Siga as dependências. getStore se resume a storage.DefaultStoreOptions() + storage.GetStore().
  5. Descubra o que é obrigatório. O define.BuildOptions tem 106 campos. Procure errors.New e if options.X == nil no corpo da função. Resultado: só o Dockerfile é obrigatório; o valor zero do Go serve para o resto.
  6. Leia o main de quem usa a lib. Em cmd/buildah/main.go, a primeira linha é if buildah.InitReexec() { return }, e o forja precisa do mesmo.

Estudo de caso: o 404 que não virava "não existe"

docker.GetDigest é o jeito documentado de pegar um digest. Para uma tag inexistente, ele devolvia um erro genérico em vez de "não encontrado". Lendo docker/docker_image.go e docker/errors.go, o motivo apareceu: no 404, ele embrulha um tipo não exportado, que o código de fora não consegue testar com errors.As. Um programa de sonda mostrou que o GET do manifesto devolve códigos testáveis, mas em formatos diferentes por registry: errcode.Error no Docker Hub e no Quay, errcode.ErrorCode no GHCR, NAME_UNKNOWN no registry local. O translate do capítulo 6 é a soma dessas descobertas.
