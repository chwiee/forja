12.1 Testes unitários com fakes

Os comandos recebem interfaces (Engine, Scanner, registry.Client), então o teste injeta fakes que só guardam o que receberam. Assim dá para provar, em milissegundos e no Windows, as regras que importam: --build-arg chega ao motor; uma imagem multi-arch é escaneada uma vez por arquitetura; uma imagem reprovada não é publicada; --immutable para antes do build; o segredo é mascarado. A política tem testes próprios: secret reprova sempre, CVE crítica com correção reprova, o teto de CVEs funciona, exceção vencida não vale, exceção sem dono é recusada.

internal/cli/cli_test.go
@@arquivo internal/cli/cli_test.go@@
internal/scan/policy_test.go
@@arquivo internal/scan/policy_test.go@@
@@saida test.txt@@

Um teste deste nível pegou um erro de desenho. A primeira versão do scan montava a referência OCI (layout.NewReference) dentro da CLI, e no Windows isso falhou porque a função valida o caminho /var/tmp/.... A correção foi tirar da CLI o conhecimento sobre o containers/image: o scan.Target passou a carregar só o diretório ou o nome remoto, e o pacote scan monta a referência.

12.2 Vulnerabilidades

Na v0.2, com o buildah dentro, o govulncheck achou problemas em duas dependências indiretas, corrigidos pedindo versões novas delas:

Vulnerability #1: GO-2026-6348  Found in: google.golang.org/grpc@v1.82.1   Fixed in: v1.83.1
Vulnerability #2: GO-2026-6253  Found in: github.com/moby/go-archive@v0.2.0 Fixed in: v0.3.0
go get google.golang.org/grpc@v1.83.1 github.com/moby/go-archive@v0.3.0
go mod tidy

Na v0.4, com Syft, Grype, Gitleaks, o SDK da AWS e Go 1.26.8, o resultado local e no CI é No vulnerabilities found. Depois de atualizar indiretas, rode tudo de novo (testes, imagem, laboratório): os autores do buildah testaram com as versões antigas, e quem garante as novas é você.

12.3 Licenças: a ferramenta não decide sozinha

Resultado para o forja v0.4: 160 Apache-2.0, 113 MIT, 73 BSD-3-Clause, 11 BSD-2-Clause, 10 MPL-2.0, 3 ISC, 2 Unlicense, e casos isolados. Três pontos exigiram leitura humana:

  • Um "GPL-2.0": github.com/spdx/tools-golang, que vem pelo Syft. O LICENSE.code do repositório diz que o código pode ser usado sob Apache-2.0 ou GPL-2.0-or-later, à escolha de quem usa. O forja usa sob Apache-2.0.
  • Cinco "Unknown": deitch/magic, in-toto/attestation e json-canonicalization são Apache-2.0, com o cabeçalho curto que o detector não reconhece. Os outros eram o próprio forja antes do arquivo LICENSE.
  • MPL-2.0 é copyleft por arquivo: pode usar; só modificações nesses arquivos precisam ser publicadas.
Ferramenta e toolchain na mesma versão

O go-licenses instalado com Go 1.26.5 falhou no projeto com Go 1.26.8 (Package go/constant does not have module info). Ferramentas que analisam código Go leem a biblioteca padrão do toolchain; reinstale-as (go install ...@versão) quando o toolchain mudar.

12.4 O que só o CI mostrou

No primeiro push, o job test falhou num passo que passava aqui:

go vet -tags containers_image_openpgp ./...
# go.podman.io/storage/drivers/btrfs
fatal error: btrfs/version.h: No such file or directory

No Windows, os arquivos _linux.go não são compilados. No Linux com CGO_ENABLED=0, os arquivos com import "C" também não. Só no Linux com cgo, que é o padrão do runner, o driver btrfs é compilado e pede os headers dele. A tag exclude_graphdriver_btrfs, que o Dockerfile já usava, faltava no vet e nos testes do CI. É a mesma lição do capítulo 10, vista de outro ângulo: cada combinação de sistema operacional e cgo é um programa diferente.
