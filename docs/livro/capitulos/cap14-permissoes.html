Por que exatamente essas 12

O erro "error setting capabilities for process" revelou o motivo. Cada RUN roda com o conjunto padrão de capabilities do containers.conf (11 delas), e um processo não pode dar ao filho o que ele mesmo não tem. Por isso o mínimo é esse conjunto padrão mais SYS_ADMIN, que é do próprio forja, para montar.

--cap-drop ALL
--cap-add SYS_ADMIN                                     (o forja: mount)
--cap-add CHOWN DAC_OVERRIDE FOWNER FSETID KILL
          NET_BIND_SERVICE SETFCAP SETGID SETPCAP
          SETUID SYS_CHROOT                             (o que os RUN recebem)

SYS_ADMIN é muito poder

Com SYS_ADMIN e root, um Dockerfile malicioso tem mais chance de escapar do container. Duas defesas: rodar num user namespace (hostUsers: false no Kubernetes), onde o root do container é um usuário comum no nó, e usar runners efêmeros e dedicados a build de imagem. O user namespace não foi testado aqui (exige um cluster Kubernetes 1.33+); ele é parte do seu desafio.

AppArmor fora do Docker Desktop

O kernel do Docker Desktop não tem AppArmor, então os testes aqui não passaram por ele. Em hosts Ubuntu (runners do GitHub, nós Kubernetes), o perfil padrão docker-default bloqueia mount mesmo com SYS_ADMIN. Por isso os workflows e o pod dos capítulos 16 e 17 usam apparmor=unconfined. não testado

Duas exigências que só apareceram no CI

  • Limite de arquivos abertos. O forja passa aos RUN o teto atual de nofile e nproc do container, e não o 1.048.576 que o buildah usaria. Assim ele funciona com o teto padrão do Docker nos runners (65.536) sem pedir CAP_SYS_RESOURCE. Se um build precisar de mais arquivos abertos, aumente o teto do container (--ulimit no Docker, ou a configuração do runtime no Kubernetes), e não as capabilities.
  • Temporários. A imagem define TMPDIR=/var/tmp. Com a raiz somente leitura, o /tmp não é gravável, e o download do banco de CVEs falhava com a mensagem enganosa database does not exist.
