19.3 A armadilha: credencial só para o host certo

O caminho óbvio seria o campo SystemContext.DockerAuthConfig do containers/image. Só que ele vale para todo registry: o forja mandaria a senha do ECR para o Docker Hub no FROM alpine, e o pull anônimo quebraria. O forja grava um arquivo de credenciais com as que já existiam mais a do ECR, e aponta REGISTRY_AUTH_FILE (buildah, containers/image) e DOCKER_CONFIG (Syft) para ele. Assim, cada credencial só é usada no host dela.

19.4 Testando o ECR com o floci

O floci (MIT, v2.1.0) emula a API do ECR em localhost:4566 e guarda as imagens num registry:2 de verdade, criado por ele. A montagem que funcionou precisou de três ajustes, cada um descoberto num erro:

  1. Rede dedicada. Com o floci na rede padrão, o proxy dele não alcançava o registry de apoio (503 Service Unavailable). A documentação de rede dele pede uma rede própria: --network floci-net -e FLOCI_SERVICES_DOCKER_NETWORK=floci-net.
  2. Nome do host. O ECR emulado responde em 000000000000.dkr.ecr.us-east-1.localhost:4566; o forja em container recebe --network host e --add-host ...localhost:127.0.0.1.
  3. HTTP. O emulador não tem TLS; --tls-verify=false. No ECR real, não.

19.5 Uma diferença do emulador, provada

No teste, o forja exists respondeu "não existe" para uma tag que o aws ecr describe-images mostrava. O log do registry apontou a causa: OCI manifest found, but accept header does not support OCI manifests. O containers/image pede o manifesto com seis cabeçalhos Accept, um por formato. Com curl:

OCI primeiro, índice OCI por último (3 cabeçalhos) via floci:  404
só o último (índice OCI):                                        404
2 cabeçalhos (docker, OCI) via floci:                            200
os mesmos 2 cabeçalhos direto no registry de apoio:              200

O proxy do floci repassa só o último cabeçalho Accept. O ECR real aceita todos, e é assim que podman, skopeo e buildah funcionam com ele. O forja não foi alterado por causa do emulador: no floci, o CI testa credencial, build, scan, push, describe-images e a imutabilidade do servidor; o exists e o --immutable são provados no GHCR.

19.6 No pipeline e no pod

examples/github-actions/forja-ecr.yml
@@arquivo examples/github-actions/forja-ecr.yml@@

No EKS, o pod de produção (capítulo 17) usa serviceAccountName: forja. A associação de Pod Identity liga essa SA à role da conta central, e nenhum secret entra no pod. A replicação do ECR para as demais regiões é configurada uma vez na conta central, e o forja publica só em us-east-1. Ela é assíncrona: se um deploy em outra região puder rodar segundos depois do push, é preciso esperar a replicação (uma evolução natural: --wait-replication).
